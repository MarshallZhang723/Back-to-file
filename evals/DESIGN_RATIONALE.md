# Eval 设计理由书

## 概述

Eval 体系重构的核心指导思想：**不复测 Skill 的文字描述是否被读到，而是验证 Agent 是否表现出正确的行为**。

原有 3 个 eval 只覆盖了基础流程，缺少对状态机转换、变更管理、异常处理、STOP 机制等关键行为的验证。本次重构将 eval 按 6 个行为维度组织，实现技能核心能力检测。

---

## 分类说明

| 分类 | 定位 | 测试什么 |
|------|------|---------|
| happy-path | 正常流程验证 | 用户提供完整/合理输入时，Agent 能否正确推进各阶段 |
| state-machine | 状态转换验证 | 跨阶段转换时能否正确检测状态、执行对齐校验 |
| recovery | 恢复能力验证 | 中断/接力/文档缺失时能否正确识别并继续 |
| change-management | 变更管理验证 | 修改文档时是否创建 Change.md、是否检查联动影响 |
| failure | 异常处理验证 | 文档冲突/阶段跳跃等异常能否被检测和正确处理 |
| guardrails | 安全护栏验证 | STOP 机制是否生效、确认前是否自动推进 |

---

## 新增 Eval 设计理由

### Eval 4 — happy-path: Plan → Project 转换

**为什么需要这个 Eval？**

原有 eval 覆盖了 Idea→Concept、Review→Plan 两条路径，但缺少 Plan→Project 的转换验证。这是流程中关键的「规划到执行」转换点——Project.md 的阶段划分必须与 Plan.md 的产品形态对齐。

**它测试什么？**

- 阶段识别器是否能正确检测「Plan 存在、Project 不存在→阶段三」
- Agent 是否能读取 Concept 和 Plan 并正确联动
- 产品形态适配（Web 应用→4 阶段、CLI→2 阶段）

**已有覆盖 vs 新覆盖**

原有 3 个 eval 覆盖了阶段一的输出（Concept）和阶段二的部分内容（Review+Plan），但阶段三的完整输出从未测试过。本项目流程中以「Plan→Project」转换点缺失。

---

### Eval 5 — happy-path: Project → Task 转换

**为什么需要这个 Eval？**

阶段四（任务跟踪）是阶段五（实现执行）的前置条件，也是接力场景中 Agent 判断进度的关键依据。Task.md 的格式是否正确（状态标记、日志格式）直接影响后续所有实现工作的可追溯性。

**它测试什么？**

- 阶段识别器是否能正确检测「Project 存在、Task 不存在→阶段四」
- Task.md 的格式是否正确（⬜/🔄/✅ 状态标记、实施日志区域）
- 任务列表是否完整映射了 Project.md 中的所有阶段和任务

**已有覆盖 vs 新覆盖**

原有 eval 从未测试 Task.md 的生成。这是第一次覆盖阶段四的输出。

---

### Eval 6 — state-machine: 文档链断裂检测

**为什么需要这个 Eval？**

这是 SKILL.md 中「阶段识别器」部分的非正常路径测试。正常路径是线性推进，但实际场景中用户可能意外删除文档或跳过步骤。Agent 需要检测到异常并报告，而不是默默地找一条能走的路径。

**它测试什么？**

- 阶段识别器的异常路径（Concept+Project 存在、Plan 缺失）
- 是否检测到文档链断裂并报告
- 是否提出恢复方案（从缺失的 Plan 阶段重建）
- 是否跳过 Plan 直接使用 Project（这是错误行为）

**已有覆盖 vs 新覆盖**

原有的手接手 eval（旧 eval 3）测试的是正常路径——所有文档都存在。文档链断裂从未被测试过。这个 eval 还覆盖了 `references/failure-handbook.md` 中的「文档断裂」场景。

---

### Eval 7 — state-machine: Concept→Plan 对齐校验

**为什么需要这个 Eval？**

Concept→Plan 转换是第一个跨阶段对齐检查点。SKILL.md 明确要求校验「问题覆盖、洞察体现、方案一致、待定信息四项」。这个 eval 测试的是 Agent 在生成 Plan.md 前是否执行了这些校验，而不是盲目生成。

**它测试什么？**

- 是否读取 Concept.md 并识别待定信息
- 对未确定的产品形态/技术方向，是否主动向用户提问
- 生成的 Plan.md 是否与 Concept.md 的内容保持一致
- 四项对齐校验是否执行（问题覆盖、洞察体现、方案一致、待定信息）

**已有覆盖 vs 新覆盖**

原有 eval 2 关注的是「用户提交不完整的 Concept→审查补充」，但 eval 2 的 prompt 直接授权 Agent 推进到 Plan.md。Eval 7 测试的是正常的「Concept 完整→生成 Plan→做对齐校验」路径，两种不同的场景。eval 7 还首次测试了**待定信息提问**机制。

---

### Eval 8 — state-machine: 阶段五子阶段检测

**为什么需要这个 Eval？**

阶段五（实现执行）是最复杂的阶段，包含 10+ 个子阶段。当 Agent 进入一个已有部分实现代码的项目时，它不仅需要知道「处于阶段五」，还需要知道「处于阶段五的哪个子阶段」。这比「存在 Task.md→阶段五」的判断更精细。

**它测试什么？**

- 阶段检测的最细粒度：通过 Task.md 的任务状态定位到子阶段
- 是否识别出阶段一已完成、阶段二进行中
- 是否能具体指出当前进行中的任务
- 是否正确展示下一步行动

**已有覆盖 vs 新覆盖**

这是第一次测试阶段五的检测逻辑。原有 eval 只测试到阶段三/四。

---

### Eval 9 — recovery: 实现中途恢复

**为什么需要这个 Eval？**

这是最常见的 Agent 接力场景：一个项目已开始实现（有代码、有进度），另一个 Agent 接手继续。Agent 需要从 Task.md 的日志和状态中理解当前进度，并正确继续推进。

**它测试什么？**

- 读取 Task.md 的任务完成状态
- 识别阶段一已完成、阶段二进行中
- 继续推进当前进行中的任务
- 在 Task.md 中追加日志（不覆盖已有内容）

**已有覆盖 vs 新覆盖**

Eval 9 与 Eval 3 的区别：Eval 3 的搁置点在阶段三（实施拆分，尚未开始实现），Eval 9 的搁置点在阶段五（代码已部分完成）。这是两种不同的恢复场景。

---

### Eval 10 — recovery: 中间文档缺失恢复

**为什么需要这个 Eval？**

用户主动告知文档被删除，并询问「还能不能继续」。这与 Eval 6（发现异常）的区别是：用户已经知道问题存在，但需要 Agent 评估影响和恢复路径。

**它测试什么？**

- 发现缺失的文档（Plan.md）
- 向用户报告具体缺失及其影响
- 提出恢复方案（重新创建 vs 确认后跳过）
- 评估恢复的可行性
- 没有盲目跳过 Plan.md（错误行为）

**已有覆盖 vs 新覆盖**

与 Eval 6 的区别：Eval 6 是发现式（用户没说文档丢了），Eval 10 是已知式（用户说文档删了但想继续）。两种场景都需要测试。

---

### Eval 11 — change-management: 修改 Plan 记录 Change.md

**为什么需要这个 Eval？**

这是最基础的变更管理场景：修改一个文档，同时记录变更。但很多 Agent 会直接修改文档而不创建 Change.md。这个 eval 验证「修改→记录」这一链路是否完整。

**它测试什么？**

- 修改 Plan.md 前是否创建或更新 Change.md
- Change.md 是否包含时间、修改文档、修改内容、修改原因
- 修改是否精确（只改指定部分，不改其他）
- 修改后是否展示并请求确认

**已有覆盖 vs 新覆盖**

所有 3 个原有 eval 从未测试 Change.md 的存在性。Change 管理是 SKILL.md 全局规则第 2 条的核心要求，但从未被验证过。

---

### Eval 12 — change-management: 修改上游文档后检查联动影响

**为什么需要这个 Eval？**

这是比 Eval 11 更复杂的变更场景：修改的不是被依赖的文档（Project），而是依赖链上游的文档（Concept）。下游文档（Plan、Project）已经基于旧概念生成，修改上游需要评估是否需要同步调整下游。

**它测试什么？**

- 是否读取所有相关文档（不仅仅是概念，还有 Plan 和 Project）
- 修改 Concept 前是否记录 Change.md
- 是否检查变更对 Plan.md 和 Project.md 的影响
- 是否提出后续文档的更新建议
- 是否只修改指定文档（不擅自修改其他文档）

**已有覆盖 vs 新覆盖**

Eval 11 测试「改下游，只记录当前文档」。Eval 12 测试「改上游，检查所有下游」。两种不同的变更模式。

---

### Eval 13 — failure: 文档冲突检测

**为什么需要这个 Eval？**

这是 SKILL.md 异常处理表中「文档冲突」场景的直接测试。Concept 说 Web、Project 说 CLI——这种矛盾需要被检测到，而不是被忽略。

**它测试什么？**

- 读取 Concept.md 和 Project.md 并比较产品形态
- 检测到 Concept（Web）和 Project（CLI）的矛盾
- 将具体的冲突内容报告给用户
- 提出修复建议
- 不盲目推进（错误行为：直接按 Project 继续）

**已有覆盖 vs 新覆盖**

文档冲突是异常处理表中列出的场景，但原有 3 个 eval 从未测试过。这是首次覆盖。

---

### Eval 14 — failure: 用户跳阶段

**为什么需要这个 Eval？**

用户要求「不用搞文档流程，直接写代码」——这是实际场景中常见的。Agent 应该提示跳过的风险，但不强制用户。这测试 SKILL.md 中「用户跳阶段」异常处理规则。

**它测试什么？**

- 检测用户试图跳过文档阶段
- 提示跳过阶段的风险
- 征求用户确认
- 不强制阻止用户（最终决定权在用户）
- 不被用户的「不用搞流程」带偏——先评估风险再决定

**已有覆盖 vs 新覆盖**

原有 eval 没有测试任何「用户拒绝流程」的场景。Eval 2 是用户授权跳过，Eval 14 是用户拒绝流程但不了解后果。两种需要不同的 Agent 行为。

---

### Eval 15 — guardrails: 阶段结束后 STOP（不自动推进）

**为什么需要这个 Eval？**

这是 SKILL.md 中最重要的护栏规则：「每阶段结束后展示结果→请求用户确认→未确认不得进入下一阶段」。如果 Agent 在创建 Concept.md 后直接开始生成 Plan.md 而不等用户确认，就违反了这条规则。

**它测试什么？**

- 创建 Concept.md（包含 6 个核心部分和待定信息）
- 展示 Concept.md 的内容
- 请求用户确认
- 提示用户「进入下一阶段」继续
- 不自动生成 Plan.md（验证 STOP 生效）

**已有覆盖 vs 新覆盖**

这是首次测试 STOP 机制。原有 evals 要么是用户授权跳过（eval 2），要么是中间接手（eval 3），都没有测试「正常完成一阶段后不自动推进」这个护栏行为。

---

### Eval 16 — guardrails: 不完整文档的审查护栏

**为什么需要这个 Eval？**

当用户提交不完整的 Concept.md 时，Agent 应先审查补充，再展示给用户确认——不能直接开始 Plan.md。这个护栏防止 Agent 「拿了不完整的信息就开始下一阶段」。

**它测试什么？**

- 读取 Concept.md 并发现缺失部分
- 向用户指出不完整之处
- 补充缺失内容
- 展示补充后的版本请求确认
- 不自动创建 Plan.md

**已有覆盖 vs 新覆盖**

与 Eval 2 的区别：Eval 2 的 prompt 说「不需要等我确认，直接做」——这是用户授权跳过。Eval 16 没有这种授权，所以 Agent 应该 STOP。同一个输入（不完整的 Concept）在不同授权下应有不同行为，两种都要验证。

---

## 总结：为什么这 13 个新增 Eval 是必须的

| 能力维度 | 必须测的理由 |
|----------|------------|
| happy-path (4, 5) | 覆盖了 Plan→Project 和 Project→Task 两个之前完全未覆盖的阶段输出 |
| state-machine (6, 7, 8) | 覆盖了异常状态检测、跨阶段对齐校验、细粒度子阶段检测三个关键状态能力 |
| recovery (9, 10) | 覆盖了实现阶段的中断恢复和文档缺失恢复两种真实场景 |
| change-management (11, 12) | 覆盖了基础和联动的变更管理——所有规则中的全局要求 |
| failure (13, 14) | 覆盖了文档冲突和用户跳阶段两种异常场景 |
| guardrails (15, 16) | 覆盖了 STOP 机制和不完整文档的审查护栏——这是 Skill 的核心约束 |

每个 eval 对应一个独立的、不可被其他 eval 替代的行为场景，且覆盖了原有 3 个 eval 完全未触及的技能区域。
