# 工作流规则

## 工作流概览

```
用户表达意图
    │
    ▼
阶段一：概念定义 → Concept.md
    │
    │  ← 🔴 CHECKPOINT：交叉校验 Concept.md 覆盖 6 个问题？
    │  ← 🛑 STOP：展示文档 → 请求用户确认 → 等待「进入下一阶段」指令
    ▼
阶段二：项目规划 → Plan.md
    │
    │  ← 🔴 CHECKPOINT：校验 Plan.md → Concept.md（问题覆盖/洞察体现/方案一致）
    │  ← 🛑 STOP：展示文档 → 请求用户确认 → 等待指令
    ▼
阶段三：实施拆分 → Project.md
    │
    │  ← 🔴 CHECKPOINT：校验 Project.md → Plan.md（功能覆盖/技术栈一致/形态匹配）
    │  ← 🛑 STOP：展示文档 → 请求用户确认 → 等待指令
    ▼
阶段四：任务跟踪 → Task.md
    │
    │  ← 🔴 CHECKPOINT：校验 Task.md → Project.md（任务一致/依赖满足/阶段状态）
    │  ← 🛑 STOP：展示进展 → 请求用户确认 → 等待指令
    ▼
阶段五：实现执行
    ├── 5.1 前端（界面骨架）
    │   ├── 5.1.1 信息布局排版（布局骨架 + 内容结构 + 排版系统）
    │   │  │  ← 技能：impeccable（layout / typeset 指令）
    │   │  ← 🛑 STOP：展示进展 → 请求确认 → 等待指令
    │   ├── 5.1.2 视觉色彩搭配（调色板 + 主题色 + 圆角 + 无障碍）
    │   │  │  ← 技能：impeccable（colorize / critique 指令）
    │   │  ← 🛑 STOP：展示进展 → 请求确认 → 等待指令
    │   ├── 5.1.3 交互动效（过渡动画 + 滚动动效 + 序列编排）
    │   │  │  ← 技能：gsap-core + gsap-scrolltrigger + gsap-timeline（实现）
    │   │  │  ← 技能：impeccable（animate / polish 指令，审查质量）
    │   │  ← 🛑 STOP：展示进展 → 请求确认 → 等待指令
    │   └── 5.1.4 Design.md（设计系统规范）→ 从前三步反向提炼
    │      ← 🛑 STOP：展示文档 → 请求确认 → 等待指令
    ├── 5.2 后端
    │   ├── DataModel.md（数据模型）
    │   │  ← 🛑 STOP：展示文档 → 请求确认 → 等待指令
    │   ├── API.md（API 设计）→ 对齐 DataModel.md
    │   │  ← 🛑 STOP：展示文档 → 请求确认 → 等待指令
    │   └── 业务逻辑实现 → 对齐 DataModel.md + API.md
    │      ← 🛑 STOP：展示进展 → 请求确认 → 等待指令
    ├── 5.3 前端交互集成
    │   └── 交互实现 → 对齐 Design.md + API.md
    │      ← 🛑 STOP：展示进展 → 请求确认 → 等待指令
    └── 5.4 部署
        ├── CI/CD 配置
        │  ← 🛑 STOP：展示进展 → 请求确认 → 等待指令
        └── 上线
    ▼
阶段六：项目总结 → Summary.md
```

## 阶段切换规则

每阶段结尾的行为是固定的：

1. **展示文档** — 把刚生成的文档完整输出给用户看
2. **交叉校验** — 对照前序文档检查内容对齐，如有遗漏先补充
3. **请求确认** — 询问用户是否满意，或者需要修改
4. **如果是修改**：修改文档 → 记录 Change.md → 重新展示
5. **如果确认通过**：提示用户手动触发下一阶段（"请告诉我「进入下一阶段」继续"）
6. **等待用户指令**：不要自动进入下一阶段

## 操作反例黑名单

| # | 反模式 | 后果 | 正确做法 |
|---|--------|------|---------|
| 1 | 不经过用户确认直接进入下一阶段 | 用户失去控制，后续文档偏离意图 | 展示→校验→确认→等待指令 |
| 2 | 跳过多平台校验直接实现 | 不同 Agent 接力时无法理解进度 | 每次回到项目先检查根目录文档状态，从现有文档继续 |
| 3 | 直接修改文档不记录 Change.md | 变更原因丢失，决策链断裂 | 每次覆盖重写前追加 Change.md 记录变更原因 |
| 4 | 同时修改代码和规范文档 | 无法区分改动来源，交叉校验失效 | 先改规范文档（记录 Change.md），再统一调整代码 |
| 5 | 跳过交叉校验直接输出文档 | 前后文档不一致，后期矛盾需重做 | 输出前先对照前序文档校验清单检查 |
| 6 | 多个文档同时修改不标注顺序 | 变更互相覆盖，版本混乱 | 一次只改一个文档，修改后立即展示确认再改下一个 |
| 7 | 用户说「继续」就批量推进多阶段 | 用户来不及决策，反悔成本高 | 每阶段展示→确认→等待指令，一次只推进一个阶段 |

## 项目文档资源速查

| 文档 | 用途 | 生成时机 | 读取时机 |
|------|------|---------|---------|
| `Concept.md` | 概念定义：6 个问题整理 | 阶段一结束 | 阶段二校验 Plan.md 时对照 |
| `Plan.md` | 项目蓝图：功能/页面/技术栈 | 阶段二结束 | 阶段三拆分任务时参考；阶段五执行依据 |
| `Project.md` | 实施拆分：阶段+任务+验收标准 | 阶段三结束 | 阶段四生成 Task.md 时参考；阶段五按顺序执行 |
| `Task.md` | 任务跟踪：状态/日志 | 阶段四（持续更新） | 阶段五每个任务完成前后更新；接力时读取进度 |
| `Design.md` | 设计系统规范：tokens/组件/布局 | 阶段五·5.1.4 | 阶段五·5.3 前端交互集成时对齐 |
| `DataModel.md` | 数据模型：实体/关系/约束 | 阶段五·5.2.1 | 阶段五·5.2.2 API 设计时对齐；5.2.3 实现时对齐 |
| `API.md` | API 设计：端点/数据结构/错误码 | 阶段五·5.2.2 | 阶段五·5.2.3 实现时对齐；5.3 前端集成时对齐 |
| `Change.md` | 变更记录：修改的文档/原因 | 有文档修改时追加 | 阶段六生成 Summary.md 时提取决策记录 |
| `Summary.md` | 项目总结：完成情况/经验/建议 | 阶段六（项目结束） | 项目归档、后续迭代参考 |
