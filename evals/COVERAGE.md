## 详细未覆盖规则列表

以下是 SKILL.md 及其参考文件中**完全未覆盖**的规则。

### 1. 阶段六: Summary.md 生成

- **来源**: SKILL.md §阶段六
- **内容**: Agent 应在所有阶段完成后生成 Summary.md，包含项目完成情况、关键决策和经验总结。
- **未覆盖原因**: 需要一个走完所有 6 阶段的长流程 eval，单次 prompt 无法完成。
- **建议**: 设计多轮 eval，或在现有 eval 中增加「手动模拟所有阶段完成」的 prompt 变体。

### 2. 阶段五子步骤执行顺序验证

- **来源**: SKILL.md §阶段五·执行总纲、workflow-rules.md 概览
- **内容**: 前端的 5.1.1→5.1.2→5.1.3→5.1.4 和后端的 5.2.1→5.2.2→5.2.3 等子步骤必须按顺序执行。
- **未覆盖原因**: 需要实际的代码生成和项目创建，超出了纯文档 eval 的范围。
- **建议**: 创建「代码级」eval，在一个已初始化的项目中测试 Agent 是否按正确顺序执行子步骤。

### 3. 前端骨架的设计解读和三旋钮设定

- **来源**: SKILL.md §5.1.1 A/B/C
- **内容**: 信息布局排版前必须声明设计解读并设定三个旋钮（DESIGN_VARIANCE/MOTION_INTENSITY/VISUAL_DENSITY）。
- **未覆盖原因**: 前端骨架 sub-stage 细节，当前 evals 未深入到代码实现阶段。
- **建议**: 创建「前端阶段」专用 eval，模拟进入 5.1.1 时的行为。

### 4. 外部技能调用验证

- **来源**: SKILL.md §阶段五 (impeccable, gsap, taste-skill)
- **内容**: 前端骨架阶段需要调用 impeccable（layout/typeset/colorize/animate）、gsap 系列、taste-skill 等外部技能。
- **未覆盖原因**: 外部技能调用依赖实际 Agent 能力，eval 框架无法 mock。
- **建议**: 添加 eval 检查 Agent 是否在生成 Design.md 或动效实现方案时引用了这些技能。

### 5. 前端预检清单（33 项）

- **来源**: validation-rules.md §5.1.1/5.1.2/5.1.3
- **内容**: 14 项布局检查 + 11 项色彩检查 + 8 项动效检查。
- **未覆盖原因**: 这些是代码级别的质量检查，纯文档 eval 无法触发。
- **建议**: 创建代码审查类 eval，提交故意违反规则的代码，检查 Agent 是否能检出。

### 6. 验证策略表

- **来源**: SKILL.md §阶段五·验证策略表
- **内容**: 根据产品形态选择验证方式（Web→dev server, CLI→直接执行, 库→运行测试等）。
- **未覆盖原因**: 需要在实现阶段验证，当前 evals 未深度到具体技术实现。
- **建议**: 创建不同产品形态（CLI、库、Landing Page）的完整流程 eval 并检查验证方式。

### 7. 多种产品形态适配

- **来源**: SKILL.md §阶段三（Project 模板说明）
- **内容**: CLI 工具跳过前端阶段，静态网站跳过后端阶段，库不涉及部署。
- **未覆盖原因**: 所有现有 eval 都是 Web 应用场景。CLI/库/静态网站从未被测试。
- **建议**: 增加非 Web 场景的 happy-path eval（CLI 工具→2 阶段 Plan→Project→Task）。

### 8. Change.md 的纯追加模式验证

- **来源**: change-management.md (Change.md 不会被覆盖，只会追加)
- **内容**: 多次修改文档时，Change.md 只追加不覆盖。
- **未覆盖原因**: 需要连续两次修改操作。Eval 11/12 只测试单次修改是否有 Change.md。
- **建议**: 创建多轮 eval：第一次修改→检查 Change.md→第二次修改→确认 Change.md 追加不覆盖。

### 9. 先改规范文档再改代码（全局规则 4）

- **来源**: SKILL.md §全局规则 4
- **内容**: 当需要修改时，先改规范文档再改代码，统一对齐。
- **未覆盖原因**: 涉及代码和文档的双向操作，纯文档 eval 无法验证。
- **建议**: 创建「规范文档→代码」一致性检查 eval，提交不一致的代码和文档，检查 Agent 是否先修规范。

### 10. 用户直接提交缺失 >3 个问题的 Concept

- **来源**: failure-handbook.md (常见场景表第一行)
- **内容**: 缺失 3 个以上问题→退回给用户重新梳理概念，而不是自行补充。
- **未覆盖原因**: Eval 2/16 测试了缺失 2 个问题的场景（自行补充）。>3 缺失的退回行为未测试。
- **建议**: 创建一个只有动机+问题（缺失 4 个）的 Concept，检查 Agent 是否退回给用户。

### 11. 连续跳过 2 个以上阶段

- **来源**: failure-handbook.md (常见场景表第二行)
- **内容**: 连续跳过 2 个以上阶段→先在 Change.md 记录决策原因，再继续。
- **未覆盖原因**: Eval 14 只测试了跳过一个阶段的全流程，没有测试连续跳过多个阶段。
- **建议**: 让用户直接要求「跳到实现」的变体 prompt。

### 12. 规范文档与代码不一致（故障场景）

- **来源**: failure-handbook.md (常见场景表第八行)
- **内容**: 先更新规范文档（记录 Change.md），再统一调整代码。
- **未覆盖原因**: 涉及代码和文档的双向操作。
- **建议**: 创建不一致场景 eval，检查 Agent 的处理顺序。

## 覆盖率数字

| 指标 | 数值 |
|------|------|
| 总 Eval 数 | 16 |
| 分类数 | 6 |
| SKILL.md 规则总数（约） | ~50 条 |
| 已覆盖规则数（约） | ~25 条 |
| **整体覆盖率（约）** | **50%** |
| 核心流程覆盖（阶段一~四） | 100% |
| 异常处理覆盖 | 40% |
| 实现阶段（阶段五）覆盖 | 15% |
| 项目总结（阶段六）覆盖 | 0% |
| 参考文件规则覆盖 | 15% |

**解读**: 50% 覆盖率意味着核心流程和关键异常场景已覆盖，但实现阶段的细节规则（前端骨架、外部技能、预检清单）和阶段六仍未触及。这部分更适合用「代码级」eval 而非「文档级」eval 覆盖。

覆盖率低不等于 bad——参考文件中的 33 项预检清单和外部技能调用是代码实现阶段的细节规则，用文档级 eval 验证既不合理也不高效。核心目标是：**文档链路上的行为全覆盖**（100%），实现阶段的质量验证留给专门的代码级 eval。
