# 故障处理手册（Failure Handbook）

## 实施故障处理

实现过程中遇到技术故障时，按以下顺序处理：

| 故障场景 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 脚手架命令失败（如 `create-next-app`） | 重试一次，检查网络连接 | 手动创建项目结构（package.json + 配置文件手动编写） |
| npm install 失败 | 检查 package.json 语法 → `npm cache clean --force` → 重试 | 使用 yarn 或 pnpm 替代，或降级依赖版本 |
| 编译/构建报错 | 读取错误日志，修复第一个报错（后续报错通常是级联的） | 回退到最近一次可编译的 commit，分步重试 |
| API 联调失败 | 检查端点 URL / 请求格式 / 认证头 | 用 curl 独立测试端点 → 如果 curl 可用则检查服务端日志 |
| 部署平台拒绝 | 检查环境变量 / 构建命令 / Node 版本配置 | 切换到备用部署平台 |
| 数据库迁移冲突 | `prisma migrate reset` 清空后重新迁移（仅开发环境） | 手动编写 SQL 脚本执行迁移 |

## 常见场景处理

所有表采用「触发条件 → 一线修复 → 仍失败兜底」三段式结构。

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 用户直接提供了 Concept.md | 审查完整性，对照 6 个问题进行评估，补充缺失项 | 缺失 3 个以上问题 → 退回给用户重新梳理概念 |
| 用户想跳过某个阶段 | 允许跳过，说明跳过后可能影响后续文档质量，请用户确认 | 连续跳过 2 个以上阶段 → 先在 Change.md 记录决策原因，再继续 |
| 用户要求修改已完成的文档 | 直接修改对应文档，并在 Change.md 中记录修改原因 | 修改后又要求改回 → 写入 Change.md 记录来回变更的决策过程 |
| 项目根目录已经有部分文档 | 检查已有文档，确定当前阶段，从缺失的阶段开始 | 已有文档互相矛盾（如 Concept 说 Web 但 Project 说 CLI）→ 写入 Change.md 记录冲突，优先使用最新版本 |
| 多个阶段文档同时存在 | 检查一致性，如有冲突则在 Change.md 中记录并优先使用最新版本 | 文档版本号/日期混乱 → 向用户提问「哪份是当前正确的？」 |
| 用户之前用过此 Skill 但中断了 | 检查项目根目录的文档状态，从中断的阶段继续 | 文档被部分修改无法判断进度 → 向用户提问「你上次做到哪了？」+ 展示发现的文档清单供用户确认 |
| 用户要求修改已实现的代码 | 先在 Change.md 记录变更原因，然后修改代码，更新 Task.md 状态 | 修改导致其他阶段文档需要同步更新 → 按「规范文档 → 代码 → Task.md」顺序逐一修改，每步确认 |
| 规范文档与代码不一致 | 先更新规范文档（记录 Change.md 说明修改原因），再统一调整所有对齐的代码 | 不一致范围太大（>50% 内容偏离）→ 向用户提议「是否重新生成该文档？」 |

## 失败处理补充

**阶段一 — 用户直接提交 Concept.md**：先审查完整性再补充，不直接使用。

**阶段五 — 遇技术故障**：如遇到脚手架命令失败、npm install 失败、编译报错、API 联调失败、部署平台拒绝、数据库迁移冲突，先按上表一线修复处理，仍失败则执行兜底方案。
